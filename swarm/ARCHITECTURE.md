## 2. Departures from the spec (decided in M0, to confirm in the decisions issue)

1. **Scope.** This repo only in v1, so the spec's product department paths and UI-redesign pilot do not apply. Task and epic schemas carry a `repo` field so other repositories can be added later.
2. **Pilot.** "Queue inspection" (a swarm-internal epic spanning core, runtime, qa and docs), not the UI redesign.
3. **States.** The spec says "11 states", but retry is an edge, not a state. Add a terminal `cancelled` state (the manager steps mention cancel).
4. **Two counters.** `maxAttempts` counts failures and lease expiries, leading to escalated, a replan, then needs-human. `maxReviewRounds` counts changes-requested rounds and goes straight to needs-human.
5. **Lease vs stall.** The manager heartbeat renews leases of running tasks (liveness). `lastProgressAt` changes only on `/progress`. The stall rule reads `lastProgressAt`. Otherwise a 30-60 minute model session would expire its lease mid-task.
6. **Dependencies.** `blocked` moves to `queued` when the last dependency merges. The queue query filters only `status=queued`.
7. **Contract tasks.** Needed only when a split touches a path matching a `contracts:` glob. Code, not the model, does the department split.
8. **Git and secrets.** The host does all git writes. The container never runs git, so it gets no `.git` mount at all (neither the common dir nor `.git/worktrees/<id>`). It gets the worktree read-write, the agent token, and no GitHub token. The spec's risk 1 mounts `.git` parts; this departs from it. M3 spike: worktree mount with `--user uid:gid --userns=keep-id` writes files owned by the host user.
9. **Repo rules.** Swarm PRs use branch `<dept>/<task-id>-<slug>` instead of `<owner>/<topic>`. The one-open-PR-per-member cap applies (it is enforced by autopilot's policy, not by GitHub). The bot's approval counts as "another member" only if it is a write collaborator and admins stay enforced.
10. **Merge race.** The orchestrator serialises merges per repo, re-checks `behind_by` before enabling auto-merge, and uses `--match-head-commit`.
11. **Subagents.** A code-driven subagent runner is the tested canonical path (the manager session emits a subtasks plan; code spawns subagents on disjoint files and applies the escalation ladder). Claude in-session subagents are supported but verified live only, because the ladder cannot be tested in CI for Claude. Needs owner confirmation.
12. **Token accounting.** Claude `--output-format json` reports usage. Codex and Gemini figures are best-effort. `policy.yaml` carries a price table.
13. **Config reload.** `departments.yaml` is read from the orchestrator's deployed checkout, reloaded on SIGHUP with full validation. Changes need an admin `git pull`.
14. **Self-hosting.** The deployed orchestrator runs older code than the pilot PRs. Store migrations are versioned with `PRAGMA user_version`. Redeploy is a manual admin step, never automatic.
15. **Bus channels.** Probed on the live bus. Findings:
    - `comm_send` does **not** create a channel. A send to an unknown channel fails with `Channel not found`.
    - Channel names must match 2-64 lowercase characters, alphanumeric plus `.`, `_` and `-`. **`#` is rejected**, so `#swarm` and `#dept-<id>` can never exist. The names are `swarm` and `dept-<id>`.
    - Only members can post. A non-member gets `You must join this channel before posting`.
    - `comm_register({ channels: [...] })` creates any missing channel and joins it. `comm_channel` create/join does the same explicitly.
    - On the live bus only `general` exists. Every swarm announcement so far (events, operator actions, monitor alerts, daily summary, intake) has failed and only been logged.

    **Fix (implemented):**
    - `channelsFor()` in `orchestrator/src/events.mjs` returns `swarm` and `dept-<id>`. `SWARM_CHANNEL` and `isValidChannelName()` live there too.
    - The `bus.send(SWARM_CHANNEL, ...)` calls in `orchestrator/bin/orchestrator.mjs` use `swarm`.
    - `shared/bus.mjs` takes an optional `channels` list and registers with `['general', ...channels]`. `orchestrator start` and the `swarm-operator` CLI pass `swarm` plus `dept-<id>` for every department in `departments.yaml`, so each identity creates and joins every channel it posts to.
    - Tests assert that every channel name the code can produce matches the bus pattern, and that registration carries the channels.

    The bus client is used only for announcements, never for state.
16. **CI.** One required job, `check`, in `.github/workflows/ci.yml` (was `autopilot.yml`). The spec's separate `swarm.yml` is not created, because a second required job would leave PRs pending when it is path-filtered. Renamed to `ci.yml`; job `check` kept. The same job also runs `shellcheck swarm/scripts/swarmctl scripts/*.sh` from the repo root; shellcheck is preinstalled on `ubuntu-latest`.
17. **Event schemas.** One envelope schema (`swarm/protocol/events/event.schema.json`) with an enum of event types, instead of one file per event. Same validation, fewer files.
18. **Generated agent files.** `.claude/agents/` is generated and gitignored. In containers it is mounted read-only at `~/.claude/agents`.

19. **Standby rule (M2).** A standby may lease only while the host has been silent for `heartbeatStaleMinutes`. Silence is measured on heartbeats from any manager whose token belongs to the host's login. A host that never sent a heartbeat counts as silent.
20. **Read access (M2).** `GET /tasks/:id` and the department queue need any valid manager token, not anonymous access. Creating an epic needs an intake token (`orchestrator token add ... --intake`).
21. **Manager tokens (M2).** Created with `orchestrator token add`, not a separate tool. Only SHA-256 hashes are stored, in a file with mode 0600, and checks are constant-time.
22. **Bus channels (M2).** Events are sent to `swarm` and `dept-<id>` with `comm_send`. The bus does not create them on first use, and `#` is not a valid character: see decision 15 for the probe results and the fix. Failures are logged and never change store state.

73. **Agent cockpit authority, checkpoints and observability (dashboard cockpit).** The cockpit is an operator view over the orchestrator's agent assignments: the orchestrator remains the normal control path, while owner/owning-manager permissions are enforced again by `agent-control.mjs` for every prompt, context change or command. The dashboard bridge caches only common assignment/session summaries and redacted feed frames; goal, task, skills, guardrails, conversation text and event detail stay per-viewer requests using that viewer's token and are never placed in the shared cache. `agent_feed.seq` is the sole replay cursor for the dashboard SSE; a dropped stream replays from the cursor and typed feed kinds are rendered as observable telemetry, never hidden model reasoning or raw prompts. Safe directives are journaled and applied only at manager checkpoints after the current model turn; interrupt/stop are explicit owner actions, preserve the worktree and record a reason. Offline dashboards remain read-only from the cached summary; writes and privileged detail wait for the orchestrator. `SWARM_AGENT_COCKPIT` is the rollout gate and can be disabled without changing swarm execution.
74. **The orchestrator is a shared manager capability.** Any authenticated member token with the `manager` role may read the orchestrator conversation and queue prompts, context updates and non-destructive commands (`status`, `pause`, `resume`, `replan`) for the orchestrator. `interrupt` and `stop`, model changes, and runtime increases remain owner-only. The orchestrator has no owning manager, so this explicit role check is the authority boundary; other agent assignments keep the owner/owning-manager rule from entry 73.
75. **Dashboard notifications stay in-page until HTTPS exists.** The dashboard derives bounded level-1 events (task needs human/failed, merged PR, finished epic, orchestrator offline/online, chat mentions/messages) from snapshot transitions and dashboard chat. Signed-in sessions receive filtered events through `GET /api/notifications/stream?after=<id>`, with a 100-event in-memory replay buffer and the existing five-stream cap. Preferences and read-through state use the 0600 users file through the authenticated preference/read routes; chat mentions are audience-filtered before delivery. The shell exposes a keyboard-accessible bell, unread count, polite toast/list, and reduced-motion-safe styling. Browser push, service workers and desktop notifications remain deferred until the dashboard is served over HTTPS.

## 3. Principles (unchanged from the spec)

1. Code controls, models judge. Queues, routing, leases, limits, retries and merges are deterministic code with tests. Models only plan, write code and review.
2. One owner per piece of state. The orchestrator's SQLite store is the only source of task state. GitHub holds code and PRs. The bus carries events and chat, never state.
3. One department per domain. Departments own disjoint path globs, so two never edit the same file.
4. Cheapest model that holds quality. Orchestrator strongest, managers mid-tier, subagents smallest. Escalate only after a cheaper step fails.
5. Everything isolated. Each task runs in its own git worktree and sandbox container.

## 4. Milestones

M0 recon and decisions (this file, README, CI and package skeleton) -> M1 protocol, store, state machine -> M2 orchestrator API and router -> M3 manager, one task at a time -> M4 review and merge -> M5 parallelism and subagents (incl. Codex and Gemini) -> M6 planner, monitoring, metrics -> M7 cut-over and pilot. Autopilot stays running until M7.
19. **Evidence in M3.** The command agent (`manager/src/agents.mjs`) marks each acceptance criterion met when its command exits 0. This is a placeholder. The review gate judges real criteria in M4.
20. **Review rounds.** A machine-gate failure is a `changes_requested` round and counts toward `maxReviewRounds`, like a model rejection. Otherwise a PR could loop on gate failures forever.
21. **Fix push.** A fix rebases the task branch on origin/main and pushes with `--force-with-lease` pinned to the head that was read. The same PR is updated; no new PR is opened.
22. **Review model access.** The review model is a command the owner supplies (`orchestrator --review-cmd "<args>"`). It reads the prompt on stdin and gets `--model <id>`. The loop is off without it. Bot approval is not implemented: the repo needs 0 approvals (solo rule), so none is needed yet.
23. **Holder.** Tasks keep `holder` (the last manager to lease them) after submit clears the lease, so fix work returns to the same manager.
24. **Escalation ladder.** Attempt 0 uses the cheapest model (`claude-haiku-5-5`), each retry steps up, the last step is kept. The ladder is checked against the policy allow-list at manager start. `commandAgent` runs a fixed command and ignores the model; real model choice for Claude, Codex and Gemini comes with the subagent runner (M5c).
25. **Role files.** `swarm/agents/*.md` are linted (model on allow-list, name matches file, no git write instructions). `manager agents install` copies them to `<repo>/.claude/agents/`, which is gitignored.
26. **Concurrency.** A manager runs up to `concurrency` tasks at once: its config value, capped by the sum of its departments' `concurrency` in `departments.yaml`, and by the machine-wide cap of 3 slots. One manager config may serve several departments (`manager init --department core,runtime`, stored as `departments`; an old config's single `department` still loads). Each tick leases from the departments in config order, department by department until the slots are full; each lease returns that department's fix work before new tasks, and a department stops being leased once its own `concurrency` cap is running. Subagents get the spec of the task's own department. `doctor` checks the spec and the queue read for each department. A leased task whose paths overlap a running task is released back to the queue (no attempt spent) and the tick stops leasing. The orchestrator does not know about overlap; the manager checks it after the lease.
27. **Repo lock.** Git operations that touch shared clone state (worktree add and remove, fetch, push) run under one in-process queue per git common dir. Commit and add stay per worktree and unlocked. One manager process per clone. A submitted task keeps its worktree for fix work; on the first daemon tick and every 10 ticks after, the manager lists `<stateDir>/wt/`, skips tasks it is running, asks `GET /tasks/:id` for the rest, and for `merged` or `cancelled` removes the worktree and deletes the local task branch under this lock. Other statuses are left alone, remote branches are never deleted, and a failed lookup or removal is logged and retried on a later pass.
28. **Subagents on the host.** Claude, Codex and Gemini subagents run as host child processes (argument arrays, prompt on stdin). The host run can read the user's home directory, so it is refused unless the manager config sets `allowHostAgents`. The container runtime (decision 38) is the production path. Gemini needs `--skip-trust` to write in headless mode, which also loads `.gemini` settings from the worktree that the repo can supply. The host runtime stays for local checks only.
29. **Plan of subtasks.** A plan's subtasks must have disjoint paths (checked before any subagent starts). After all finish, each changed file must belong to the subtask whose paths match it. Subagents run in parallel in one worktree, which is safe only because the paths are disjoint. Evidence is the same placeholder as commandAgent: exit 0 means met, judged in M4. On the default task path, `subagentAgent` first asks the model for a subtasks plan (`protocol/subtasks.schema.json`, paths inside the task paths, roles from `agents/`). A valid plan with 2+ subtasks goes to `runPlan`; an unparseable, invalid, out-of-scope or overlapping plan, or a one-subtask plan, falls back to the single implementer (logged). A change outside every subtask fails the task. The planning call runs read-only (claude `--permission-mode plan`, codex `-s read-only`, gemini `--approval-mode plan`); if it still changes a file, the edit is reverted and planning counts as failed (single implementer).
30. **Per-kind ladders.** Claude and Gemini have default ladders. Codex has none: its ids are the owner's pick, so the manager config must set `ladder`. Codex is refused until its ids are on the allow-list.
31. **Lease liveness.** The manager heartbeat renews the leases of the tasks it reports running (departure 5, now implemented). The daemon beats every 60 s while any task runs, so `once` mode renews too. The orchestrator checks for expired leases every 60 s; an expired lease spends an attempt.
32. **Operator actions.** `orchestrator task resolve|replan|cancel <id> --reason "..."` moves needs-human, escalated or any non-terminal task. A reason is required and goes into the task history. Actions run on the DB directly from the CLI, which then announces the change on `swarm` and `dept-<id>` itself (text prefixed `operator <action>:`, `cancel` is `task.cancelled`). The send is awaited for at most 5 s; a dead bus only logs a warning and never changes the outcome. `--no-bus` skips it; `--bus-url` and `SWARM_BUS_MCP_URL` apply as for `start`.
33. **Token accounting.** Claude subagents report billable tokens from the JSON `usage` block: input + output + cache creation. Cache reads are excluded, since they repeat context each turn. Gemini subagents report billable tokens from the JSON stats block (stats.models.<model>.tokens prompt + candidates). Codex subagents report billable tokens from the `codex exec --json` event stream: for every `turn.completed` usage block, (input_tokens - cached_input_tokens) + output_tokens. Codex counts cached input inside input_tokens and reasoning inside output_tokens, so cached input is subtracted (cache reads, as with Claude) and reasoning is not added twice. A reply with no usage block reports 0.
34. **Planner.** The model proposes tasks by local key; code assigns ids. A proposed task whose paths cross departments or touch contract globs is split by the router into one subtask per group. Contract subtasks land before every work subtask in the plan. A path no department owns is rejected (the router's `platform` fallback is for live routing, not planning). Planning uses `planModel` from policy.yaml (default Opus, on the claude allow-list). Two tasks on overlapping paths must be ordered with `dependsOn`. A cycle, an unknown key, a size over `maxTaskSize`, or more than 60 subtasks stops the plan. An epic that already has tasks is not planned twice.
35. **Monitor.** `evaluate(snapshot)` is pure. Rules and thresholds: manager_down after 2 min without a heartbeat; stalled warn at 15 min and critical at 25 min without progress (in_progress only, uses `lastProgressAt`); budget warn at 80% of token budget, stop at 100% (cancels the open task); minutes budget: warn at 80% and `stop.budget_minutes` at 100% of `budget.minutes` for an `in_progress` task, measured from the latest lease in its history (or the latest fix resume), so a requeued task restarts the clock (cancels the open task, same as `stop.budget`); attempts warn when one attempt is left; unowned path; main_red from the base branch checks; queue depth above 10 per department. Alerts are deduped per condition: once, again on severity change, after the clear, or after a 60 min cooldown. Heartbeats are persisted in SQLite.
36. **Metrics.** `GET /metrics` (manager token) computes from the store: status counts, queue depth per department, leases held, total and over-budget tokens, review rounds, and for merged tasks lead time (created to merged, median and mean, minutes) and tokens per merged task. `GET /dashboard` is served without data. The page asks for a manager token, keeps it in sessionStorage (per viewer, never in the URL), and reads `/metrics` with a bearer header. CSP blocks all external resources. A one-line summary goes to `swarm` at the first monitor tick of each UTC day.
37. **Main red revert.** When the head of main goes red, the monitor's main_red alert carries the sha and the orchestrator reverts the PR behind it. The revert is an ordinary task: its own epic (source `monitor`), department `platform`, priority p0, size M, paths exactly the culprit PR's files. Gates, review loop and humanReview rules apply, so a revert of a policy or `.github` file goes to a person. The revert agent is deterministic (`git revert --no-commit <sha>`, no model). Guards: one revert per sha; a PR titled `Revert PR #...` is never reverted; a head with no PR (direct push) is skipped and alerted.
38. **Subagent container runtime.** Production runs use `runtime: container`: one throwaway container per subagent, image `swarm-subagent:1` built from `swarm/sandbox/Dockerfile` with pinned CLI versions. The container gets the worktree at `/work` (rw), the auth file of the CLI being run only (ro, at that CLI's home path), and no host environment, so no GitHub token. Caps: drop ALL capabilities, no-new-privileges, memory, CPU, pids. The host runtime stays behind `allowHostAgents` for local checks. On timeout the named container is removed (`rm -f`), not only the client process. Network is still open: the model API needs it. Limiting egress is a follow-up.
39. **Intake and MCP endpoint.** `orchestrator start` polls open issues labelled `epic` (default every 5 min, `--intake-interval`, or `intake.intervalMinutes` in policy.yaml; `--no-intake` turns it off; `orchestrator intake --once` runs one pass). An issue becomes an epic (source `github`) only if its author AND the person who last applied the `epic` label (issue events) are in `autopilot/members.json`, compared case-insensitively. Otherwise it is skipped with a log line that has the issue number and reason, never the text, and its text never reaches the planner (prompt-injection rule; the spec's risk table is not in this repo, so the rule is implemented as its issue states it). Dedupe: epics carry `issue_repo` and `issue` columns (migration 3) with a unique index, so one issue gives one epic across restarts. Planning stays an explicit step: with `--plan-cmd` each new epic is planned at once, without it the epic stays `open` for `orchestrator plan`. A planner failure is logged and leaves the epic open. The orchestrator also serves `POST /mcp` (JSON-RPC 2.0, one JSON reply per request, no sessions). Any valid token may connect; tools check roles: `swarm_status`, `swarm_queue`, `swarm_task_get` need `manager`, `swarm_epic_create` needs `intake` (decision 20). `scripts/mcp-bridge.mjs` is untouched.
40. **Deploy.** `swarm/deploy/`: user units for the orchestrator, managers, and a nightly backup timer (03:17, Persistent). Env templates carry no secrets; the GitHub token line stays commented until issued. `orchestrator backup --out <file>` uses VACUUM INTO and never overwrites. Runbook: `swarm/deploy/RUNBOOK.md`. The server admin installs; nothing here touches a running service.
41. **Dispatcher.** The orchestrator runs two more loops inside `start` (`--no-dispatch` turns both off). (a) Bus listener: every 10 s (`--listen-interval <s>`) it reads its bus inbox and handles new direct messages. `ready`, `blocked <task> <reason>` and `help <text>` are honoured only from senders that are managers in the token file; from anyone else they are logged and ignored, as is other text. `ready` starts a dispatch pass at once; passes are coalesced (at most one running and one pending, so a burst of `ready` costs two passes). `blocked` and `help` become `warn` alerts on `swarm`, collapsed to one line of at most 200 characters, once per sender and kind per 10 min. A message that throws is not replayed: the listener advances its id per message. `comm_poll` cannot block for this: the bus has no mark-read over MCP, so old unread mail makes every poll return at once; the listener keeps the highest message id instead and persists it in the store (`meta` table, migration 4). After a restart it handles the direct messages newer than the stored id, but only those under 30 min old (`created_at`, UTC), so a long outage does not replay a `ready` flood; on the very first run (no stored id) it records the newest id and handles nothing. `comm_inbox` has no offset or since parameter, so it cannot be paged: when a full batch of 100 starts after the stored id, a warning logs that messages may have been skipped. (b) Dispatch pass: every 2 min (`--dispatch-interval <s>`) and on `ready`, `planDispatch()` (pure) joins manager tokens, heartbeats and the bus agent list. A manager is online only when its last heartbeat is under 2 min old (heartbeats are the source of truth); a bus name alone does not make it online, it only earns the nudge below. A manager is idle when online with free slots. Each department's queued tasks go to idle managers that cover it, best task first, split by free slots. Each idle manager gets a direct message `dispatch: <n> task(s) queued in <dept>, next <id>. Lease now.` (once per manager and task per 10 min). A department with queued tasks and no online manager raises `dispatch.no_manager` on `swarm`, and each bus-online covering manager without a heartbeat still gets one nudge so it wakes and heartbeats. Dispatch stays pull: the manager still leases through the API, so a spoofed message only makes a manager ask early. A manager started with `--bus-url` says `ready free <n>` to `swarm-orchestrator` when it goes idle, and during its idle sleep checks its inbox every 5 s and wakes on a `dispatch:` direct message. Without `--bus-url` it polls every `pollSeconds` as before. Bus reads (`inbox`, `agents`, `getState`) never throw: malformed output logs one warning and returns null, and the waker treats a failed read as no dispatch.
42. **Orchestrator on one machine.** The orchestrator runs on one workstation, not the server. Every orchestrator model call (review, planning) runs on the owner's own `claude` and `gh` logins, so the owner controls usage and input. Planning stays manual (`orchestrator plan`) unless `--plan-cmd` is given. The server keeps the jobs that use no model: the bus, a watchdog (`scripts/watchdog.mjs`, timer every 2 min) that posts on `swarm` when the orchestrator goes down or comes back, and copies of the nightly DB backup (`SWARM_BACKUP_PUSH`, scp from that machine). The user unit keeps a read-only system and home except `~/.swarm` and the CLI state dirs; `swarmctl install` pins `PATH` in the env file because user services do not get the login shell's PATH. When that machine is off, the swarm pauses: leases expire and retry.
43. **Portable orchestrator.** No component hard-codes the orchestrator's address. At start and every 10 min the orchestrator writes `{url, host, at}` to bus state `swarm/orchestrator` (`--public-url` overrides the URL). Managers (`--url bus`) and the watchdog (`SWARM_ORCH_URL=bus`) read it. Bus state is writable by any bus member, so a manager checks a looked-up URL before sending its token: `POST /whoami {manager, nonce}` must return `HMAC-SHA256(key = sha256(token) hex, nonce)`, which only a server holding `managers.json` can compute; the token is never sent to an unverified URL. A manager re-resolves when the orchestrator stops answering, so a move needs no change on member machines. `swarmctl export` packs the DB (VACUUM INTO), `managers.json` and the env file into a mode-0600 archive; `swarmctl import` installs on the new machine with its own Tailscale address and PATH, keeping the token line. One orchestrator at a time: export stops the old one.
44. **Guardrails.** Risks the swarm must not turn into a bad merge, the guard for each, and the test that proves it. The machine gate (`gates.mjs`) is pure; it receives `pr.changes` (`filename`, `status`, `patch`, `previous_filename` from the GitHub PR files API; `patch` is missing for binary or very large files, which the secret scan cannot see). Deletion guards route to needs-human like `humanReview` paths; the others block.

    | risk | guard | where | test |
    |---|---|---|---|
    | 1. Mass or protected deletion | More than `limits.maxDeletedFiles` (default 10) deleted files, or any deleted file (or rename source) under `protected:` globs, goes to needs-human, never auto-merge | `gates.mjs`, `policy.yaml` | `gates.test.mjs` guardrail 1 |
    | 2. Files outside the task | Every changed file must match a task `paths` glob, else a blocker per file | `gates.mjs` | `gates.test.mjs` guardrail 2 (the guard predates the machine gate) |
    | 3. Unsafe git push or branch delete | `assertSafePush` (pure) runs before every manager `git push`: only the task's own branch (the worktree's real HEAD branch, fully qualified), never the base branch; plain `--force`, `-f`, `+refspec` and a lease without a 40-hex sha are refused; deleting any other remote branch is refused (see 21) | `git-safety.mjs`, called from `worktree.mjs` `push`/`pushForce` | `git-safety.test.mjs` |
    | 4. Secrets in the diff | Added lines matching `ghp_`, `github_pat_`, a private key or `GH_TOKEN=` block, as does an added `.env` or `.env.*` (not `.env.example`); findings name file and pattern, never the match | `gates.mjs` | `gates.test.mjs` guardrail 4 |
    | 5. Runaway swarm (kill switch) | Bus state `swarm/paused` (any value pauses; `orchestrator resume` writes `{paused:false}`, so resume is also bus state). The orchestrator caches the flag, refreshed every 10 s; a failed read keeps the last value, so a bus blip never unpauses. While set: lease returns `{tasks: [], paused: "..."}` (managers read `tasks` only), dispatch passes do nothing, the review loop leaves submitted tasks waiting (no model call, no auto-merge armed), and the monitor raises `alert.paused` (warn). 70. **Time the machine sleeps does not count.** The orchestrator and the manager run on one workstation, so a suspend freezes both. Awake time over the budget still cancels, as before. A restart of the orchestrator starts with an empty log; a sleep across a restart is not seen.

76. **The server deploys main by itself.** Merged work went live only when someone ran `swarmctl upgrade` over ssh, so a member's merged pull requests sat undeployed until an operator was around; only the operator has a shell on the server. Now `swarm-autodeploy.timer` (every 5 min, `deploy/server/`) runs `swarmctl autodeploy` on the server: it fetches `origin/main` and, when it moved, runs the normal `upgrade` (backup when an orchestrator is installed, fast-forward, `npm ci`, restart, health check, rollback and maintenance flag on failure). A merge to `main` with a green `check` is therefore live within about 5 minutes with no owner step, and members never get a shell on the server. A sha whose upgrade failed is written to `~/.swarm/autodeploy-failed` and skipped until `main` moves again (or the file is deleted), so a broken merge is not retried and rolled back every 5 minutes; the fix is a new merge. `flock` on `~/.swarm/autodeploy.lock` keeps runs from overlapping. The timer is not part of `all`, so `upgrade` and `restart` never touch it; `swarmctl logs autodeploy` shows its runs. Trust: anyone who can merge to `main` now runs code on the server as the owner's user; the protection is the required `check` and the write-access list on GitHub. Only the server installs the timer: the orchestrator and managers still upgrade by hand, since the orchestrator holds the GitHub token and the model logins.
77. **Dashboard maintenance state.** While the dashboard is being changed, its pages said nothing: actions failed and the page went blank on restart. Now a flag file on the dashboard machine (`DASH_MAINTENANCE_FILE`, default `~/.swarm/dashboard-maintenance.json`, mode 0600: `reason`, `by`, `since`, `auto`) puts it in maintenance. The server reads it on every request: `GET /health` (no sign-in) and `GET /api/snapshot` return `maintenance: { reason, since, overrun }` or `null`, an unreadable file still counts as on, and `overrun` is true after 30 min (`MAINTENANCE_OVERRUN_MS`) so a failed or forgotten upgrade shows. While it is on, operator actions and chat channel create/delete get 503 `dashboard maintenance: <reason>`; sign-in and chat posting stay open. Every page loads `/maint.js`, which probes `/health` every 10 s and shows a bar at the top (maintenance, overrun, or "restarting" while the server does not answer), and reloads the page when the server answers again after being down, so pages pick up new code. `swarmctl maintenance on [reason]|off|status` sets it by hand. `swarmctl upgrade` and `restart dashboard|all` set it only when no flag exists and only on a machine with the dashboard installed, and clear only their own flag once the dashboard answers `/health`; a failed upgrade rewrites it as `upgrade to <sha> failed (<step>); rolled back to <sha>` and leaves it on. Not posted on the bus.
